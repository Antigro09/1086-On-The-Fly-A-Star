# Development Mac planning measurements

These CPU-only measurements characterize this Java implementation on the authorized Mac. They establish no roboRIO/Systemcore deadline guarantee, physical motion safety, combined robot-program performance, or Java-versus-C++ speed ratio. Actual robot integration remains on hold. A native rewrite has not been implemented or benchmarked.

## Host and method

MacBook Pro Mac17,7, Apple M5 Max, 18 CPU cores, 128 GB RAM, macOS 26.6.2 AArch64. Primary runtime: Temurin 17.0.20.1+1. Secondary runtime: Temurin 25.0.4.1+1 executing the same common release-17 classes. Each run uses one worker, one pending slot, a fixed 128 MiB heap, and sequential caller submission. Ambient OS load and GC counts/time are in every raw summary. No artificial competing load or GPU work was generated by this task. Ambient load does not establish an isolated host. Browser/server and real perception/NT/robot periodic workloads were not running during these baseline runs.

The generic 8×4 m fixtures use a 0.1 m grid, a 0.4×0.4 m raw robot footprint and 0.02 m backend-owned clearance. Obstacles are physical circles plus enclosing uncertainty/motion margins; the real adapter conservatively converts these to boxes. The moving case includes 0.1 m uncertainty plus 1 m/s motion for 0.2 s age and a 0.2 s request horizon. The narrow passage, full barrier, clutter, open field and cancellation workloads are synthetic; they are not a specific FRC season's geometry. Fixture hashes are in the summaries.

Primary measurements call actual `AStarPlannerBackend.plan(Request)` with a fresh monotonic search budget per request. Each workload has 100 warm-up and 500 measured samples in a fresh JVM; a second fresh JVM repeats the adapter run. The elapsed measurement deadline is 10 ms; the search timeout is separately 100 ms. A miss is caller submission-to-result latency above 10 ms even if the typed solver outcome arrives successfully. No planner-frequency promise follows from these distributions.

`end_to_end_ns` includes worker submission/wakeup and result delivery. `worker_wall_ns` includes synthetic request construction and the backend call; core mode also includes map/input preparation. `reported_ns` measures the whole adapter or the separately invoked core solver. The two phases are separate calls; subtracting their timings is not an exact adapter-overhead measurement. Worker allocation counters measure allocated bytes, not retained heap/RSS; worker CPU time is separately recorded. The 240 s overall cap, 2 s per-future wait and fixed sample/options bounds keep this a small development tool.

Cancellation is a deterministic 256-poll probe. Trigger-to-return excludes external scheduling, cancel dispatch, periodic-thread delay and GUI round-trip. The empty-grid optimization changes polling frequency and therefore the search progress reached at poll 256; before/after cancellation-workload latency is not equivalent work. A true deadline may win before the probe and is retained as `TIMEOUT` by the current harness.

Baseline source: `6255196698e27683fdc7ecd98a72ebe576b197be`.

| cluttered | 3.052 | 3.219 | 3.409 | 3.849 | 0/500 | SUCCESS 500 |
| narrow-passage | 0.911 | 1.070 | 1.156 | 1.672 | 0/500 | SUCCESS 500 |
| no-path | 2.984 | 4.066 | 6.752 | 13.018 | 1/500 | NO_PATH 500 |

The baseline repeat had no 10 ms misses and maxima below 4.9 ms. The first no-path maximum of 13.018 ms is retained as observed, rather than discarded. p99 with 500 samples is exploratory; it is not a hard bound.

The measured change caches whether the immutable owned static grid contains any occupied cell. `SweptCollision.safe` skips static cell scans only when this flag proves them empty. It still checks field boundaries, all dynamic envelopes, and cancellation. Nonempty static maps use the original cell collision tests. This applies directly to the v1 adapter, whose physical occupancy is supplied as obstacle envelopes and whose static cell array is empty. It does not relax robot footprint inflation or collision conservatism.

The optimized repeat also had no 10 ms misses; cluttered p99 was 1.618 ms and no-path p99 1.274 ms. Path statuses and separately measured expansion counts were unchanged for the non-cancellation fixtures (clutter 880, narrow 444, no-path 1088, moving 568).

Allocation was not substantially reduced: median bytes/request remained about 370,088 for clutter, 194,864 for narrow, 383,504 for no-path and 285,144 for moving. The first optimized run recorded 11 GC collections totalling 8 ms over the full run. This is cumulative collection time, not a measured maximum GC pause or retained-memory bound. Larger synthetic 16×8 m no-path work allocated a median 1,767,096 bytes/request and reached p99 8.683 ms/max 9.294 ms with 200 measured samples after 50 warm-up. No 10 ms misses occurred in that small large-field run, but it shows workload scaling.

A separate actual 1 ms search budget produced typed `TIMEOUT` for all 500 cluttered requests, 318/500 no-path requests, 1 narrow and 2 moving requests. Other no-path samples returned `NO_PATH` when the bounded graph was exhausted in time. Caller deadlines can still be exceeded by dispatch, exception unwinding or result delivery after the search notices expiry. A timeout is not proof that no route exists.

On JDK25 with common Java17 bytecode, optimized cluttered p99 was 1.547 ms/max 2.021 ms and no-path p99 1.417 ms/max 2.107 ms; all six workload statuses were expected and there were no 10 ms misses. This verifies execution on this Mac's JDK25, not Systemcore native libraries, WPILib deployment or controller performance.

## Profile and language decision

A separate JFR profile run used `settings=profile,maxsize=32m`; it is excluded from headline latency. First planner stack-frame observations most often named `SweptCollision.safe` (86), `Run.poll` (19) and `MapSnapshot.occupied` (11). These are sampled observations, not exact CPU percentages or independent inclusive costs. Sampled allocation stacks also point to grid-centre poses, queue nodes and solver arrays. The retained profile summary is in the evidence directory; the local full recording is `build/benchmarks/baseline-profile.jfr`.

The evidence supports keeping the Java contract/backend and fixing measured algorithmic costs before considering a language rewrite. Java currently satisfies this Mac's chosen 10 ms measurement threshold on these optimized samples. It has not proven that threshold under the intended controller's combined periodic, vision, NT and planning load. C/C++ can only be compared fairly after an equivalent collision contract, cancellation, validation, fixtures and native implementation exist; none is authorized or provided here. Controller measurements and safety/packaging boundaries should determine any later migration.

## Reproduce

Use JDK17 with the pinned Gradle 8.5 wrapper:

```sh
./gradlew --no-daemon --max-workers=1 plannerBenchmark \
  -PbenchmarkArgs='--warmup 100 --samples 500 --out build/benchmarks/current'
```

For the exact fixed initial/max heap used above, compile the benchmark then invoke its classpath with `java -Xms128m -Xmx128m`; the recorded command transcript in `docs/benchmark-commands.md` gives standalone commands. Use `--phase core` only as a separately labelled invocation. `--timeout-ms 1 --deadline-ms 1` tests actual deadline expiration. `--width-m 16 --height-m 8 --warmup 50 --samples 200` runs the bounded larger fixture. Supply an explicit JDK25 executable to repeat the common Java17 artifact there; keep Gradle itself on JDK17.

Raw CSVs, environment summaries, fixture hashes and a host manifest are retained locally under ignored `docs/evidence/mac-benchmark/`; generated recordings are excluded from the public source branch. The portable [command transcript](benchmark-commands.md) and the aggregate results above are published. The initial recorded CSVs predate the harness's per-sample detail column and preserve status plus each summary's last detail; they cannot reconstruct mixed resource/deadline causes. Current runs retain each detail and aggregated detail counts. The SPI maps resource limits into typed `TIMEOUT`, while the detail preserves the solver's underlying cause. These tests did not hit a resource limit.

[Controller benchmark procedure](benchmark-procedure.md) remains unrun and requires separate authorization and identified target/load. A browser/HTTP polling run, if recorded separately, characterizes only that desktop load; it is not a full robot stack benchmark.

The current harness was additionally checked with a 0.01 ms search budget, 20 warm-up and 50 measured samples per workload: all 300 outcomes were `TIMEOUT`, including deadline winning before poll-count cancellation; details were retained. This is a timeout smoke test, not a clean latency benchmark. An initial attempt accidentally invoked stale standalone classes and reproduced the old cancellation assertion; recompilation of the current source fixed that test.
